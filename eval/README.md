# Mini eval-сет

`dataset.json` — 16 вопросов, размеченных вручную по реальному содержимому
корпуса. Одна запись:

```json
{
  "id": "q01",
  "language": "ru",
  "question": "На скольких языках и в скольких экземплярах составляется договор?",
  "expected_clause_id": "5.3",
  "expected_source_file": "corpus_raw/contracts/contract_01.pdf"
}
```

Покрытие — минимум два вопроса на каждый из пяти документов: 5 по `contract_01`,
4 по `contract_02`, 3 по `contract_03`, по 2 по `contract_04` и `contract_05`.
Языки: русский, казахский, английский.

Каждый `expected_clause_id` открыт в исходном файле и сверен глазами. Вопросы
писались после индексации корпуса, по фактическому тексту, а не по догадкам о
том, что в договоре может быть.

## Запуск

Нужны заполненный `.env` (Supabase, `GENERATION_MODEL`, `JUDGE_MODEL`),
проиндексированная таблица и запущенные модели.

```bash
uv run python eval/run_eval.py
```

Скрипт ходит в живой Supabase и дважды в LLM на каждый вопрос, поэтому он
намеренно вынесен из `tests/` и не собирается pytest'ом. Прогресс печатается по
мере готовности: локальные модели считают минутами, и молчащий скрипт неотличим
от зависшего.

Логика судьи (`judge.py`) при этом тестами покрыта — `tests/test_judge.py`
гоняет её на фейковом провайдере без сети.

## Ограничение датасета

`expected_clause_id` — одно значение, как требует тикет. Там, где ответ законно
лежит в соседних пунктах (например `Section 10.1` и `Section 10.1.1`), засчитан
будет только указанный. Это делает метрику строже, чем есть на самом деле.
